# Compatibility with the fork (Python)

English | [简体中文](compat.zh-CN.md)

The goal is to be a **drop-in replacement**: commands, arguments, standard output, exit codes, the data directory, `credentials.json`, and the table schema and content format of `messages.db` all match the fork, so callers (such as programs that parse `已发送 msg_id=…` ("sent msg_id=…"), `OK …/EXPIRED …`, or the position at the start of each history line) don't need to change.

## Module mapping

All of the fork's features have been rewritten; for new features, see the "New" row of the differences table below.

| Module | Original files (fork) | This repository | Verification |
|---|---|---|---|
| Protocol assets: gateway packets, long-lived connection frames, full gateway definitions, API mapping | `larkx/proto/*.proto`, `lark_all_pb2.py`, `cmd_map.json` | `assets/`, `proto/proto.proto` | Rebuilt by the pipeline below; the API mapping is byte-for-byte identical to the original, the full definitions are a superset of the original's (plus the namespaces registered as arrays, see the differences table), and `proto.proto` adds edit-version and Markdown fields on top of the original (see the differences table below) |
| Login and credentials: QR code, cookie import, credentials check | `larkx/auth.py`, `region.py` | `src/auth.ts`, `src/region.ts` | Tested for real: import / check / QR initialization; credentials fields match the original |
| Gateway client and message long-lived connection | `larkx/client.py` | `src/client.ts` | Tested for real: sending 5 kinds of messages, mark as read, message links, search, fetching history, receiving the echo over the long-lived connection |
| Message decoding (25 types) / request building | `larkx/proto/decoders.py`, `builders.py` | `src/proto/` | Compared item by item against parity fixtures generated by the original Python code |
| Local storage (SQLite / MySQL) | `larkx/storage/` | `src/storage/` | The same test suite runs against SQLite and MySQL 8.4; reading a database written by the Python version gives byte-for-byte identical output |

## Verified byte for byte

- `lark config`, `auth status`, `auth check`, `chats`, `sessions`, `messages` (including `--json`, `--anchor`), `history` (including `--json`), `api` (including printing raw bytes as `b'...'`), `search`, `self-chat`: both versions give identical output on the same data (2026-10-13, reading the `~/.larkx` written by the Python version).
- Message content decoding (18 types + the text for decode failures), push frame parsing, building all outgoing packets, and response decoding: `tests/parity.test.ts` checks against fixtures generated by the original.
- Storage format: `content_data` matches Python's `json.dumps(ensure_ascii=False)` (separators, escaping, int64 without precision loss, float `1.0`, bytes replaced with `<n bytes>`, truncation to 20,000 characters); time columns use SQLAlchemy's `YYYY-MM-DD HH:MM:SS.ffffff`.
- Downloaded resource files, the terminal QR code ASCII art, agent session ids (uuid5), protocol assets, and all intermediate outputs of the pipeline (except the fields added to `proto.proto` later: `editVersion` / `editTimeMs` of `entities.Message`, `markdownIds` of `RichText`, and the `proto.binpb` and `core.binpb` rebuilt as a result; and the namespaces registered as arrays that the pipeline extracts since 2026-11-10, which add to `schemas_all.json` and `lark_all.proto` / `.binpb`).

## Intentional differences

| Aspect | Fork | This repository | Reason |
|---|---|---|---|
| Iteration order of protobuf map fields | upb hash table slot order (fixed across processes for the same set of keys, but unrelated to both insertion order and wire order) | Wire order | The original order carries no meaning, and replicating the upb hash table would be fragile with no benefit. Affects: key order of map fields in `content_data` (JSON semantics unchanged); the order in which multiple text segments are joined in system message summaries; the processing order of multiple messages in the same push packet; the wire order of map entries in outgoing packets (the server doesn't depend on it) |
| Multiple messages in the same push packet | Dispatched to another event loop and processed concurrently | Processed serially in arrival order | Storage order is deterministic, so callers reading by auto-increment id never see messages out of order |
| Network-layer error text | The requests exception text (e.g. `HTTPSConnectionPool(...): Read timed out.`) | `网络请求失败(<host>): <原因>` ("network request failed (<host>): <reason>") | Different runtimes, so the text can't match; the word "网络" ("network") is kept, so callers' rule of recognizing network problems by "网络 / timed out" still holds. The text for non-2xx HTTP responses (`400 Client Error: Bad Request for url: …`) matches requests |
| Reason for gateway errors | Only requests' `400 Client Error: …` | Same text, with ` (<reason>)` appended when the gateway gives a reason in the response (`lark api` and uncaught exceptions); in the library it is in `HttpError.reason` | The reason (e.g. `chat not in thread mode`) directly tells whether it's a problem with arguments, permissions, or the chat type |
| Uncaught exceptions | Prints the Python stack trace, exit code 1 | Prints only one line, `<error type>: <message>`, exit code 1 | Callers usually take the last line as the message, so the result is the same |
| Log lines | `time \| level \| module:function:line - message` | `time \| level \| module - message` | Only the function name and line number are dropped |
| Location of `.env` | python-dotenv searches upward from the package directory (the repository root for an editable install) | The current working directory (loaded automatically by Bun) | A single-file executable has no "package directory"; when needed, put a `.env` in the caller's working directory or pass environment variables directly |
| Interactive menu when credentials expire | questionary arrow-key selection (falls back to a numbered menu when unavailable) | Numbered menu | One less interactive dependency; same options and behavior |
| Library entry point | `larkx/__init__.py` exports the client, credentials, storage, and agent | Exports only the parts that run under both Node and Bun (credentials, client, long-lived connection, resource download, logging interface) | Storage and agent depend on Bun, and in-process embedding (e.g. niuma) doesn't need them; the CLI still has everything |
| Long-lived connection keepalive | websockets defaults: 10-second handshake timeout; protocol-level ping every 20 seconds, disconnect if no pong within 20 seconds | 15-second handshake timeout; application-level heartbeat every 30 seconds, disconnect if no frame at all arrives within 65 seconds | Node's WebSocket has no protocol-level ping; the server answers every application-level heartbeat with a frame, which tells whether the connection is still alive |
| Reconnection | Reconnects directly; messages during the disconnection are lost | After reconnecting, backfills messages missed while disconnected from the chats that changed in the inbox (chat messages and thread replies), deduplicates by msg_id, saves them to the local database, and hands them to the digital twin | The digital twin must not miss messages from people looking for it |
| Digital twin prompt | `<message>` has only the chat, sender, time, and content | When someone replies to another message (quote reply or thread reply), there's an extra `<quote>` line with the quoted message's sender and original text; without a quote it matches the original | Seeing only replies like "可以" ("OK") or "同意" ("agreed"), the digital twin can't tell which message the other person is responding to |
| Reaction events | Reaction pushes are not handled | The long-lived connection decodes reaction changes (who added / removed which reaction on which message), and `listen` logs them; with `LARKX_AGENT_REACTIONS=true`, reaction changes others make on my messages are handed to the digital twin (`<reaction>`); `lark config` has an extra `agent_reactions` item | Lightweight confirmations such as treating a thumbs-up as "approved, go ahead" |
| Send failures | Fails outright (`sendMsg` returns None) | On network errors, 5xx, or when no message id comes back, automatically retries twice with the same message cid (the server deduplicates by cid, so no duplicates are sent); only if it still fails does it return null / throw, and `SendUnconfirmed` carries the cid back | The digital twin's replies shouldn't be lost to a single network blip, and retries must not produce two messages |
| Markdown elements | MARKDOWN elements in rich text (tag 49, common in bot messages) aren't included in the summary; `content_data` has no `markdownIds` | The summary includes their content as written; the `richText` in `content_data` gains `markdownIds` | For Markdown messages sent by bots, the original's summary is empty and the digital twin can't see the content |
| Recall and edit | The same message pushed again over the long-lived connection is ignored as a duplicate | Messages carry `recalled` / `edited` markers (present only when true); `listen` replaces the content of recalled messages in the local database with `[已撤回]` ("recalled") (clearing `content_data`) and edited ones with the new content; queued recalled messages are no longer handed to the digital twin, edited ones are replaced with the new content, and ones already processed are handed to it again with `<edited>true</edited>` | If the other person recalls or changes their question, the digital twin must not keep answering the old content |
| Command permissions | None; every command can run | Before running, checks against `LARKX_ALLOW` / `LARKX_DENY` or the current account's rules in `permissions.json`; exit code 126 when not allowed; exits with an error (exit code 1) when the rule configuration is invalid. With no configuration, behaves like the original. The library's `LarkClient.create` can enable the same checks with the `permissions` option (throws `PermissionDenied`); not checked when it isn't passed | Limits what the digital twin can do, e.g. read-only, or no adding members and no recalls |
